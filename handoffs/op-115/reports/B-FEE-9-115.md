### Open: Sol B-661-3 (round 3, not started because of the PAUSE)
`applyPaymentIntentFailed` matches by PaymentIntent id with no status fence. A delayed earlier decline therefore flips a paid, successfully retried purchase to `payment_failed` and removes its entitlement.

Proposed design (fixes only this finding):
- Prefetch, out of tx, for `payment_intent.payment_failed`: when the matched row is not `pending` / `payment_failed`, retrieve the PaymentIntent and pass `paymentIntentStatus[piId]`.
- In the handler:
  - Claimable rows: CAS update `where { id, status in (pending, payment_failed) }`. A count of 0 means a success won, so no-op.
  - Settled rows, PI `succeeded` or another non-failure status: no-op (stale or superseded failure).
  - Settled rows, PI `requires_payment_method` / `canceled`: apply as today. This keeps real async (hosted-checkout) failures.
  - Settled rows, provider status unknown: throw, so the webhook tx rolls back and Stripe redelivers.
- Tests:
  - failed -> succeeded -> delayed old failure stays paid (red before);
  - concurrent success/failure;
  - ordinary decline control;
  - async real failure on a paid row control.
- Test stubs need `clientPurchase.updateMany` (or `update` with a status predicate) honouring the status filter.
