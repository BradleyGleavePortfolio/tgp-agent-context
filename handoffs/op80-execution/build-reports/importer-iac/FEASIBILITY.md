## KICS: genuine native support, but not a demonstrated coverage replacement

KICS explicitly supports scanning GitHub workflow `.yml` and `.yaml` files under its **CICD** platform; this is native input support, not merely an Action that runs a scanner. Its CLI supports `--type CICD`, JSON reports, default failure on all finding severities, and `--ignore-on-exit none`. ([platform documentation](https://github.com/Checkmarx/kics/blob/master/docs/platforms.md), [CLI documentation](https://github.com/Checkmarx/kics/blob/master/docs/commands.md))

The official current CICD index lists these four native GitHub queries; no token-permission or untrusted-checkout query is listed there. ([CICD query index](https://docs.kics.io/latest/queries/cicd-queries/))

| Native query | ID | Published severity |
|---|---|---|
| Run Block Injection | `20f14e1a-a899-4e79-9f09-b6a84cd4649b` | High |
| Script Block Injection | `62ff6823-927a-427f-acf9-f1ea2932d616` | High |
| Unsecured Commands | `60fd272d-15f4-4d8f-afe4-77d9c6cc0453` | Medium |
| Unpinned Actions Full Length Commit SHA | `555ab8f9-2001-455e-a077-f2d0f41e2fb9` | Low |

Consequently, **KICS alone is not established as preserving the existing native permission regression** (`CKV2_GHA_1`, original ci.yml missing an explicit permission declaration). This absence is a limit of the inspected official index, not a claim that no future/custom rule could exist; adding custom policy is not the requested minimal native replacement. ([CICD query index](https://docs.kics.io/latest/queries/cicd-queries/), [preserved native checkpoint](file:///home/user/workspace/operator80/execution/importer-iac/NATIVE_GREEN_CHECKPOINT.md))

KICS is a feasible native workflow scanner, but I do **not** recommend replacing Checkov with it on the current evidence: rule coverage differs, the reviewed CLI page does not establish complete parsed-file inventory/error semantics, and no exact binary/query bundle or vulnerability status was verified. Its broader IaC platform support does not itself establish Fly.toml-specific policy coverage. ([CLI documentation](https://github.com/Checkmarx/kics/blob/master/docs/commands.md), [platform documentation](https://github.com/Checkmarx/kics/blob/master/docs/platforms.md))

## Smallest plausible alternative to investigate, not implement

If the operator permits a workflow-only equivalent, **one pinned standalone zizmor binary** is a narrower candidate than introducing KICS plus additional custom permission policy: zizmor officially supports offline native `excessive-permissions`, `template-injection`, `insecure-commands`, and `dangerous-triggers` audits, and distributes standalone prebuilt binaries on a best-effort basis. This is a feasibility recommendation, not proof of equivalence, compatibility, or a clean dependency inventory. ([native audits](https://docs.zizmor.sh/audits/), [supported installation options](https://docs.zizmor.sh/installation/))

Required constraints for a separately approved prototype:

1. Use a supported exact release **at least 1.21.0** for documented no-input exit 3; independently verify its actual binary hash/provenance, platform compatibility, dependency inventory and advisory status before accepting it. No exact release/hash is selected or verified here. ([exit behavior](https://docs.zizmor.sh/usage/), [binary caveats](https://docs.zizmor.sh/installation/))
2. Explicit offline operation, `--strict-collection` (default parse handling only warns), versioned `--format=json-v1`, and failure on every nonzero exit. Do not use SARIF, `--no-exit-codes`, automatic fixes, or lower severity filters as a substitute for blocking behavior. ([usage and exit contracts](https://docs.zizmor.sh/usage/))
3. Preserve clean allowlisted environment, trusted isolated configuration, exact-head/dirty-tree and trigger contracts. Inspect and prove inline-ignore/config/persona behavior before claiming all-applicable enforcement: regular persona is not all results, auditor persona includes probable false positives, and offline mode omits online-only audits. A flat findings array also does not by itself prove every expected file was parsed; a native per-file or other authoritative inventory strategy needs validation. ([configuration, personas, input collection and JSON](https://docs.zizmor.sh/usage/))
4. Obtain explicit R120 equivalence authorization and a bounded ownership decision before any edits; neither zizmor nor KICS satisfies the literal Checkov command, and zizmor is not a Dockerfile/Terraform/Kubernetes/Fly.toml scanner replacement. The currently frozen workflow-only scope must not be described as full canonical R120 closure. ([R120](file:///tmp/tgp-op80-cycle2-inputs/context/AGENT_RULES.md), [zizmor audit types](https://docs.zizmor.sh/audits/))
