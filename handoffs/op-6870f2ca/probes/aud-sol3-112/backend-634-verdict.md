### B-634-2 — PARTIAL: initial-claim failures still disappear; retained rows can pin the recovery page

**Initial-claim boundary:** `src/scheduling/jobs/reminder.job.ts:250-263,410-423,540-570` still creates a first durable delivery row only when the session is inside its due band. If that insert fails with a real non-P2002 DB failure at the band's final tick, no unfinished row exists for the new recovery pass. Independent actual-job/emitter probe: a confirmed session starts in 55m; both first claim inserts raise Prisma P2024, leaving zero logs; DB and transports recover, clock advances the real 5m interval, session is now 50m away, and the next sweep produces **zero logs / zero in-app / zero push**. The prior nominal non-P2002 test reruns at the same clock; neither it nor the new existing-row tests proves this boundary. [Candidate job/tests](https://github.com/BradleyGleavePortfolio/growth-project-backend/pull/634), [original claim-error/recovery requirement](https://github.com/BradleyGleavePortfolio/growth-project-backend/pull/634#issuecomment-5955780870).

**Recovery-page liveness:** `reminder.job.ts:421-422,454-464` always takes the oldest 200 rows, but deliberately retains moved-future revisions without changing their eligibility/order. A larger backlog does not necessarily drain as the new comment promises. Independent probe seeds the explicitly supported retained-future state for 200 older rows on distinct coaches, then one valid same-revision retry for a session 50m away; across three advancing 5m ticks the first page never changes and the eligible row stays `retry`, with **zero sends**. Its session can start before those old future revisions reach their new bands. The predicate/index alone does not provide fair progress. [Candidate recovery implementation and retained-future fixture](https://github.com/BradleyGleavePortfolio/growth-project-backend/pull/634).

**Minimal fix:** make first-claim failure/missed-tick recovery durable or boundedly discoverable without relying on the failed insert having succeeded, preserving kind/revision/recipient fencing and correct 24h retirement. Give retained/not-yet-eligible work a next-eligible schedule or use a bounded, resumable/keyset recovery scan so it cannot permanently pin the oldest page. Add actual-cadence first-insert failure and backlog-with-retained-prefix tests, including the 24h counterpart; do not solve this by removing recovery or turning launch reminders off.
