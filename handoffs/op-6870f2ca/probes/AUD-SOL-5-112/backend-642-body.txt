## What turns the button on (backend and mobile agree)

Backend (read-only code reading at 3bd6215b):
- `src/auth/google-verifier.service.ts:48-58` `getAudiences()`: `GOOGLE_CLIENT_IDS`, split on commas and trimmed, with empty entries dropped. It falls back to `GOOGLE_CLIENT_ID`. `:60-62` `isConfigured()` returns `audiences.length > 0`.
- `src/auth/auth.service.ts:936`: `googleEnabled = supabaseConfigured && this.googleVerifier.isConfigured()`. `:943` adds `'google'` to `providers`. `:957` sets `google_signin_enabled: googleEnabled`.
- The sign-in itself, `POST /auth/google` (`auth.service.ts:975-1010`), checks the Supabase session token with `supabaseAdmin.auth.getUser(token)` and requires a Google identity. It does not use `GOOGLE_CLIENT_IDS`. The env var only controls whether the policy advertises Google, plus the `provider=google` ID-token branch of `/auth/recent-auth-token` (`auth.service.ts:1977`).
- The manifest loader rejects an empty or blank entry before any write (`scripts/fly-env/fly-env-manifest.js:129`). This matches the `ENV_RULES` validator (`src/common/env-validation.ts:261-277`).

Mobile (main 2c17c241):
- `src/lib/signupPolicy.ts:93-100`: `googleEnabled = providers.includes('google')` when `providers` is an array. Only when `providers` is missing does it read the legacy field, and then only an explicit `google_signin_enabled === true` counts. Unknown or failed policy means Google is hidden (`STRICT_SIGNUP_POLICY` / `UNKNOWN_SIGNUP_POLICY`, `:60-66`, `:138-144`).
- `LoginScreen.tsx:116-118,222-225,545` and `CreateAccountScreen.tsx:196-197,267,985,1380` render "Continue with Google" only when `policy.googleEnabled`. Both screens fetch the policy on mount.
- `src/utils/googleAuth.ts`: Supabase `/auth/v1/authorize?provider=google` goes to `tgp://auth/callback`, then `POST /auth/google` runs with the Supabase access token.

**What installed builds show after apply:** after the apply and the restart, the policy returns `providers:["email","google","apple"]` and `google_signin_enabled:true`. Every build that reads the policy shows "Continue with Google" on Login and Create Account the next time either screen mounts. No app update is needed, and nothing changes for email or Apple. The only policy fields that change are `providers` and `google_signin_enabled`.

**Known gap (not caused by this PR):** in-app account deletion for Google-only users. Mobile main re-authenticates with `{ provider: 'google_session', provider_token }` (`DeleteAccountScreen.tsx:290`, `services/api.ts:1027-1034`). Backend main accepts only `provider` in `['google','apple']` (`src/auth/auth.dto.ts:501-505`), so that call gets a 400 until backend #608 (adds `google_session`) is deployed. This is already true today for anyone who signed up with Google earlier. Turning Google on makes the path reachable for new users, so #608 has to be deployed before App Review (App Store 5.1.1(v)).

## Sequence (docs/runbooks/launch-flags.md)

1. The operator merges this PR.
2. `Fly Env Sync (operator)`, `mode=plan`. Expected row: `GOOGLE_CLIENT_IDS | secret | github-secret | absent | absent | set | not on Fly`, `Plan: 1 to set, 0 to unset`. The plan never prints the value (pinned by `test/ci/fly-env-sync-behavior.spec.ts:717-728`).
3. `mode=apply confirm=SET`, plus `deploy_staged=true` if no backend deploy is coming in this window (one rolling restart, then proof inside every started machine). Otherwise the staged value rides the next deploy.
4. Check: `GET /api/auth/signup-policy` returns `"google"` in `providers` and `google_signin_enabled:true`.

**Rollback / kill:** if the name is absent there is no audience, so Google is not advertised. Open a one-line PR back to `"unset"` and apply it with `deploy_staged=true`. In an emergency, run `fly secrets unset -a backend-spring-lake-3890 GOOGLE_CLIENT_IDS` first (runbook section 5). Mobile hides the button on its next policy fetch.
