### B-312-1: the new toggle's failure path shows one generic message for every error, with no reference ID and no Sentry report
- **Evidence:** `NotificationPreferencesScreen.tsx:192-204`.
  - Any rejection from `notificationsApi.updatePreferences` gives `Alert.alert('Could not save preference', 'Please check your connection and try again.')`.
  - It does not read the status or machine code. A 400 (for example, an older backend rejecting the new fields, the very path the PR body names), a 401 or a 5xx all tell the user to check their connection, which is false for them.
  - An unknown failure shows no request ID and is not reported.
  - This is the binding no-generic-errors rule (owner 13:34). This PR routes a new control through the path and documents it as the designed failure behaviour, so it is in scope.
- **Minimal fix:** in that catch, branch on the error.
  - No response (network): keep "Could not save your workout reminder setting. Check your connection and try again."
  - 401: route through the existing auth-failure handling (log in again).
  - 4xx/5xx or unknown: "Your workout reminder setting could not be saved, so it was left as it was. Try again in a moment, or contact support with reference <request_id>." Report it through the existing `reportUnexpected` (`src/lib/consultation/report.ts:15`).
  - Add one test per branch.
