### B-305-5: the runbook's staged rollout bypasses the guard and drops the clinic profile env from the update
- **Evidence:**
  - `docs/OTA_UPDATES.md:162` says "For a risky change use `--rollout-percentage` with the raw command only after the dry run passed".
  - The guard's own header (check 5) and `publishEnv` (`scripts/eas-update-guard.js:228`) exist because `eas update` does not apply eas.json `build.<profile>.env`.
  - A raw `eas update --channel clinic` therefore builds the bundle without clinic's `EXPO_PUBLIC_FF_*` values: CONSULTATION_ONBOARDING, CLIENT_TUTORIAL, COMMUNITY_DM=false and the others.
  - The guard has no rollout option (`:297` passes only channel, environment and message).
- **Impact:** for the clinic rollout cohort, the riskiest update is the one shipped through the unguarded path. It silently flips clinic features in the delivered JS.
- **Minimal fix:**
  1. Add `--rollout-percentage <1-100>` to the guard: validate it as an integer from 1 to 100, and pass it through to `eas-cli update` with `publishEnv`.
  2. Change line 162 to use the guard only.
  3. Add a test that the child gets the flag and the profile env.

### B-305-6: errors from OTA-delivered JS reach Sentry unsymbolicated, and step 5 cannot be done as written
- **Evidence:**
  - Source maps are uploaded only at EAS build time (`@sentry/react-native/expo` plugin, `metro.config.js` Debug IDs; README "Sentry release tracking").
  - An `eas update` bundle has new Debug IDs and no uploaded maps. The guard publishes and exits (`:297-300`).
  - The release stays `<version>+<build>` (`src/services/sentry.ts` `buildReleaseId`), so `docs/OTA_UPDATES.md:163` "Watch Sentry for the new release" has no new release to watch.
- **Impact:** after the first hotfix, every unknown error from the updated JS arrives with minified frames. The owner rule needs unknown errors in Sentry to be actionable, and OTA is the day-1 hotfix path.
- **Minimal fix:**
  1. After a successful publish, have the guard run `npx sentry-expo-upload-sourcemaps dist`, with `SENTRY_AUTH_TOKEN` from the EAS env. If the token is missing, give a named next step; if the upload fails, exit non-zero.
  2. Change step 5 to filter Sentry by the update id (the SDK's expo-updates context) or the channel.
  3. Add a test that the upload runs only after a status-0 publish.
